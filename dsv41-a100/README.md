# DeepSeek-V4.1-Flash を A100 (sm_80) で動かす — 自作ランタイム

コード: [shi3z/deepseekv4.1-A100-custom](https://github.com/shi3z/deepseekv4.1-A100-custom)
モデル: dim 5120, 40 層, 384 エキスパート top-6, moe inter 2304, o_lora 1024 x 8 グループ
環境: A100 80GB PCIe x8（1.94 TB/s 理論、SXM ではない）

DeepSeek のスタックは Hopper/Blackwell を要求する。sm_80 で V4.1 を走らせるものが
他に無いので、推論ランタイムを自分で書いた記録。

## 設計

- 層をパイプラインで GPU 間に分割
- **dense 重みは FP8 のまま**: レジスタ内で E4M3→bf16 を厳密復号（ビット配置 + x2^(s−7)）、
  `mma.m16n8k16`、約 1.15 TB/s
- **エキスパートは FP4 で VRAM にパック**: grouped tensor-core GEMM
- デコード層を融合: 層あたり約 100 launch → **約 26 launch**
- Engram はホスト RAM
- GPU セグメントごとに CUDA graph 1 枚

行数で 3 つの FP8 dense カーネルを使い分ける:

| 行数 | カーネル | 方式 |
| --- | --- | --- |
| ≤ 16 | `fp8_tc.cu` | x を mma の A フラグメントに |
| 17–64 | `fp8_tcw.cu` | 重みを A、トークンを B（タイルあたり8）、x タイルを cp.async で smem、重みは 2 反復先まで 2 組のレジスタに |
| > 64 | `fp8_tcg.cu` | CUTLASS 式 64x128x128 タイル、8 warp、両オペランドに ldmatrix |

全部が重みを 16-k グループ内で k 置換して読む。**この k 置換が ldmatrix のワードを
そのまま A フラグメントにする**のが鍵。効果:

| M | 置換前 | 置換後 |
| --: | --: | --: |
| 32 | 468 GB/s | **766 GB/s** |
| 64 | 233 GB/s | **575 GB/s** |

落とし穴: parity で添字を付けたレジスタ配列は local memory に落ちる。明示的に 2 組書くこと。

## スループット

4-GPU EP（shard 100/100/100/84）、64 混合プロンプト:

| 同時列数 S | MTP なし | K=3 | K=5 |
| --: | --: | --: | --: |
| 1 | 63 | 84 | — |
| 8 | 237 | 285 | 301 |
| 16 | 340 | 398 | 360 |
| 32 | 478 | **528** | 473 |
| 64 | 737 | 674 | — |
| 256 | 1769 | — | — |
| 1024 | **2415** (424 ms/step, ctx 512) | — | — |

1 レプリカあたり約 2.4k tok/s で飽和する。1 行あたりのコストは約 0.35 ms で平坦になり、
エキスパート側はトークン/エキスパートとともに伸び続ける。
8-GPU パイプライン 51.9 tok/s、7-GPU EP で B=1 65.7 tok/s、
独立した 4-GPU レプリカ 2 本を B=32 で回して**合計 911 tok/s**（相互干渉なし）。

**MTP (DSpark) は厳密。** greedy では接頭辞一致、サンプリングでも
点質量ドラフトに対する per-row sample-and-compare 規則は Leviathan の
投機サンプリングと一致する。受理数は K=5 で 2.1 ドラフト/step、K=3 で 1.63、K=1 で 0.75。
**K の選択は S に依存する**: K=5 は 8 列まで、K=3 は 40 列まで、それ以降は無効
（交差点が約 44 列）。

128 行での層あたり内訳: attn+hc 1.44 ms、自分のエキスパート 1.74 ms
（shard の 100 中約 90 が触られ、約 1 TB/s）、partial 待ち 0.21 ms、層計 3.6 ms。
**エキスパート段が床。** 2000 tok/s の合計を出すには、dense カーネルを速くするのではなく
層あたりのユニークエキスパート数を減らす（タスク条件付きバッチ）かレプリカを増やすしかない。

ルーティングのテレメトリ: タスクごとに層あたり上位 64/384 エキスパートが
ルーティング質量の 83〜95%、上位 128 で 96〜99.8%。タスク間 JS 距離 0.56〜0.80 bit。

## 測って外れたもの（記録として）

| 案 | 結果 |
| --- | --- |
| **ホットエキスパートの静的レプリカ**（Strata 式） | **全 S で遅い**（S=1 59.9→50、S=8 221→200）。ルートパケットはどうせマルチキャストされ NVLink バイト数は不変、ピアのエキスパート作業は既に隠れており、ローカルレプリカは所有者のクリティカルパスに 17.9 MiB の読み出しを足すだけ |
| 全ピア待ちの除去（上限値） | S=1 で +8%、P2P 完全無料でも +12% |
| 融合 persistent エキスパートチェーン | 同等〜−5%。per-element FMA の FP4 カーネルは SM issue bound、動的 atomic work claiming は静的割り当てに負ける |
| 融合 dense チェーン（`[wq_a; wkv]` 連結） | **+0.7〜1.1%**（ビット厳密）。小さいが本物 |
| FP4 デコード除去 | +2%（= デコードは律速ではない） |
| 8-warp ブロック / 128 行 FP8 ブロック / warp staggering | 効果なし |

**ルーティング局所性は未知のプロンプトでは弱い**: GPU あたり 4 GiB のキャッシュが
リモートルートの 19% しかカバーせず、`P(E_{L+1}|E_L)` の recall@8 は 43%。
トークンごとの prefetch には約 390 GB/s が必要になる。

## エキスパート圧縮の研究

**可逆圧縮は死んでいる。** ペイロードのエントロピーは 3.893/4 bit、
どのコンテキストモデルも held-out で 3.75 bit に飽和し、
ブロック構造もエキスパート構造も無い（独立性の対照実験が最近傍統計を再現する）。
エキスパート丸ごとの最良比は 0.89 で、しかも 15 GB/s のデコーダが必要になる。
zstd/lz4 はストリーミングを**遅く**する。

**形式の無料の改善 2 つ**: E8M0 スケールはモデル全体で 11 種類しか値を取らない
（4 ビット化で 0.971倍、HBM トラフィックも −2.9%）。FP4 コードの 0 と 8（±0）は
数値的に交換可能（`fp4_gemm_tc`/`fp4_gemv_pairs` を通してビット一致を確認）。

**非可逆が本番。** 4 重みグループの VQ をコードブックごと E2M1 にスナップすると
量子化後の重みが正しい FP4 ニブルのままなのでカーネル変更なしで評価できる。
wikitext-2 PPL (ctx 2048, 16 chunks, 全 40 層):

| 構成 | PPL | 対ベースライン | 圧縮比 |
| --- | ---: | ---: | ---: |
| ベースライン | 3.0765 | — | 1.000 |
| **混合 平均 3.5 bit** | **3.1002** | +0.77% | **0.853** |
| 一律 3.5 bit | 3.1295 | +1.72% | — |
| 一律 3.0 bit | 3.2067 | +4.2% | 0.735 |

校正を考慮した符号化（diag ヘシアン）は一律構成には効く (3.2067 → 3.1867) が
混合構成には効かない: **3 ビットに落とされる cold エキスパートの 95% は
校正トークンを 2304 個も見ていない**。

## 可逆のみの制約下での天井

FP4/INT4 変換・低ランク・枝刈り・疎性・非可逆 KV・近似 attention・
ルーティング改変をすべて禁じた場合の S=1 の実測（3 プロンプト）:

| 構成 | tokens/pass | tok/s |
| --- | ---: | ---: |
| ベースライン | 1.0 | 68.7 |
| ドラフト 4 | 3.66 | **117** |
| ドラフト 5 | 3.80 | 111（遅い） |

レバーは K 行検証パス: verify(2 行) = 21.0 ms 対 1 行 14.5 ms（+6.5 ms）。
バッチ経路は S=1 専用カーネル（FP8_M1 / FP4_M1 / LEAN / INDEX_FAST はすべて B==1 限定）を
全部失うため。以降は 1 行あたり約 1.9 ms。
**カーネル/ランタイムだけなら 72〜75 tok/s が現実的上限**（物理限界 ≈130 は到達不能）、
厳密 MTP の K 行経路に lean カーネルが入れば 130〜150。

`wq_b`/`wo_b` の GEMV は 1.26〜1.31 TB/s で、同カーネル自身の長ストリーム速度 1.63 TB/s に
届かない。差は 42 MB カーネルあたり約 7 µs の固定 ramp/tail で、
**A100 では回収できない（PDL が無い）**。このボックスの DRAM コピー上限は 1.57 TB/s。

## 計測上の注意

**このランタイムは実行ごとにビット再現しない。** ベースライン対ベースラインで
初手ロジットの cosine 0.9966〜0.9976、greedy 200 トークンのうち一致は 9〜18 個
（`DSV41_DETERMINISTIC=1` でも 160 中 124）。
最初に分岐する層は 4 または 18。**正しさの検証はこのノイズフロアに対して判定する必要がある。**
温度 0 の出力がバッチ構成で変わるのも同じ理由（M 依存のカーネル選択が丸めを変える）。

カーネルは **CUDA graph の中で計測する**こと（さもないとホストの launch gap 約 40 µs が支配する）。
重みは 40 MB の L2 を越えて回す。
