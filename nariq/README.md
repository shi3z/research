# NariQ — 2.94 bpw trellis 符号化器を自分で書く

対象形式: `nari-labs/nari-llama.cpp` の NariQ v1（trellis 量子化 GGUF）
対象モデル: Qwen3.8-27B（26.889 G パラメータ、64 ブロック中 48 が linear-attention）
環境: A100 80GB x1 ・ 2026-11

公開されている `nari-labs/Qwen3.8-27B-NariQ-GGUF` は 3.0 bpw。
その**形式を読み解き、符号化器を独立に実装し、より小さいファイルで同等品質に到達**した記録。
英語の詳細版は [FINDINGS-en.md](FINDINGS-en.md)。

## 結果

| モデル | バイト数 | bits/weight | wikitext-2 PPL (ctx 2048, 32 chunks) | 対 BF16 平均 KL | top-1 |
| --- | ---: | ---: | --- | ---: | ---: |
| BF16 | 53,808,276,736 | 16 | 6.1963 ± 0.0831 | — | — |
| 公開 NariQ 3.0bpw | 10,123,626,592 | 3.010 | 6.3523 ± 0.0835 | 0.1089 | 86.2% |
| **こちら: 3bit ブロック + 2bit 埋め込み + 16帯域ヘッド** | **9,895,557,568** | **2.943** | **6.3774 ± 0.0863** | 0.0839 | 87.7% |

**0.067 bpw 小さくして PPL は 0.025 差**。しかもブロック側は*一律*3ビットで、
参照実装の 2〜6 ビット混合割り当てに頼っていない。
1 A100 で全モデル符号化 48.9 分、デバイスメモリは常時 12 GiB 以下。
`llama-simple -ngl 99` で **40.9 tok/s**、「The three laws of robotics are:」に
アシモフの三原則をそのまま返す。

## 形式について分かったこと

**リバースエンジニアリングは不要だった。** fork に `nariq/FORMAT.md` があり、
`ggml/src/ggml-trellis.cpp` が素の C++ ホストデコーダなので、符号化器は
「実際に読む側のデコーダ」に対して検証できる。

**ビットストリームと tile 並びは EXL3 のものがビット単位でそのまま。**
16x16 タイルは 256 位置のリング、位置 p の 16 ビット状態はリングビット
[(p+1)k−16, (p+1)k) を MSB 先頭で読み、末尾は巻き戻す (tail-biting)。
NariQ の要素マップは EXL3 の**転置**。

**ただしコードブックは EXL3 の mul1 ではない。** 両者とも状態に `0x83DCD12D` を掛けるが、
EXL3 は積の 4 バイトを丸ごと足すのに対し、NariQ は各バイトの**上位 6 ビット**を足して 126 を引く:

```c
uint32_t x = state * 0x83DCD12Du;
int v = ((x >> 2) & 63) + ((x >> 10) & 63) + ((x >> 18) & 63) + ((x >> 26) & 63) - 126;
```

相関 0.998 だが最大 0.1（単位分散単位）ずれるので、mul1 で採点した Viterbi は
NariQ のコードブックでは採点されていないことになる。
fork 自身の `nariq/NOTICE` は事後的に「exllamav3 の tile 符号化・tile 内順序・
tensor-core 順序・INT8 グリッド用の MUL1 乗数」を謝辞しており、
**乗数は借りたがコードブックは違う**という、まさに差分の場所を言い当てている。

## 効いた一手: 周波数帯域分割ヘッド

公開ファイルは出力ヘッドをトークン頻度で 16 帯域に分け、先頭帯域に 6 ビット、
次に 4、3、残りに 2 を与えている。ヘッドだけを量子化して run A のブロックに
接合すると、その寄与だけが切り出せる:

| ヘッド | bits/weight | PPL | BF16 ヘッド比のコスト |
| --- | ---: | --- | --- |
| BF16 (run A) | 3.583 | 6.3686 | — |
| 一律 3bit | 2.969 | 6.4448 | +0.0762 |
| **16帯域 6/4/3/2** | **2.943** | **6.3774** | **+0.0088** |

**帯域ヘッドは小さく、かつ PPL コストが 9 分の 1。** 16 帯域のうち 12 が 2 ビットなので
0.36 GiB 対 0.44 GiB、しかもモデルが実際に出すトークンは 6 ビットと 4 ビットを保つ。
参照実装がやっていて効いていたのはこれ一つで、しかも重みの性質ではなく
**語彙の頻度分布の性質**。だからブロック側をどれだけ作り込んでも見つからない。

## 失敗した二つと、その共通の原因

ablation（1行ずつ1箇所だけ違う）:

| 構成 | bits/weight | PPL | 切り出しているもの |
| --- | ---: | --- | --- |
| A: 一律3bit ブロック + BF16 ヘッド | 3.585 | 6.3686 | — |
| graft: A のブロック + 3bit 符号化ヘッド | 2.970 | 6.4448 | ヘッド符号化: **−0.615 bpw に対し +0.076 PPL** |
| B: + 対角ヘシアン `pre` 重み付け + post 再フィット | 2.970 | 6.4977 | 重み付け: **同サイズで +0.053 PPL** |
| + モジュール別ビット割り当て（重み付けなし） | 3.016 | 6.4940 | 割り当て: **+0.125 PPL** |

**対角ヘシアン重み付けは、最適化している量を改善しながら品質を落とす。**
モジュール単位では活性重み付き誤差を 10〜60% 削ったのに、端から端では
何も買えず 0.05 PPL 失った。理由は二つあり、同じ方向を指す:

- **対角はヘシアンではない。** 列ごとの再スケールは対角にしか合わせられず、
  列間に相関を残した誤差はこの指標から見えない。
- **Hadamard の前に列をスケールすると incoherence が下がる。** それは trellis が
  必要としている性質そのもの。16倍スケールされた列は回転後の行列における構造で、
  Viterbi はそこにビットを使わされる（Frobenius 誤差 0.132 → 0.137〜0.166）。

割り当てが失敗した理由も同じ根: imatrix は**入力側の感度しか持たない**。
`h` はモジュールの入力チャネルの二乗平均なので、`ffn_down` の出力誤差が
残差ストリームに直接乗ることと、`in_proj_a` の誤差が DeltaNet ゲートを通ることの
区別がつかない。さらに `h` は異なる空間を読むモジュール間で比較不能
（隠れ状態のチャネル power 0.34〜198、FFN 中間は 3.3e-6〜9.2e-3 で 4 桁違う）。
結果、割り当て器はモデルを担っている行列（`ffn_down` / `out_proj` / `gate_proj`）から
ビットを奪い、48x5120 の DeltaNet ゲートに与えた。

**直し方は良い割り当て器ではなく、出力側を含む感度。** 逐次量子化器 (LDLQ) が
副産物として出す Gauss-Newton / 全ヘシアン推定か、各モジュールの損失寄与の直接測定。

## 符号化器の素の性能

3.0 bpw 割り当てが各ビットレートに与えたモジュール群の、校正重み付けなしの
相対 Frobenius 誤差の中央値（Qwen3.8-27B の実際の重み）:

| bits | モジュール数 | 相対誤差（中央値） | 2^−bits |
| ---: | ---: | ---: | ---: |
| 2 | 50 | 0.2620 | 0.2500 |
| 3 | 14 | 0.1320 | 0.1250 |
| 4 | 13 | 0.0670 | 0.0625 |
| 5 | 20 | 0.0345 | 0.0312 |
| 6 | 1 | 0.0181 | 0.0156 |

`2^−bits` は無限次元量子化器のガウス率歪み限界なので、16 状態の記憶しか持たない
trellis がその **5〜8% 上**に着地するのは期待通りで、それがガウス標的ではなく
実際の重み行列で成り立っている。比較として、同じデータに対する最良の
4 レベル*スカラ*量子化器 (Lloyd-Max) は 0.3428 — それが 2 ビットで trellis 構造が買うもの。

## 参照実装の符号ベクトルの正体

**片側につき符号ストリームは一本で、全モジュールが共有している。**
`sign(trellis_pre)` は同じ K を持つ全モジュール（全層・全種類）で同一で、
5120 要素のベクトルは 17408 要素のものの先頭 5120 要素に完全一致する。
`sign(trellis_post)` は同種の第二ストリーム（入力側との一致率 0.49 = 独立）。

デコーダからは区別できない（各テンソルが自分の `pre` を持つ）。得なのは推論時で、
`H diag(su) x` がその活性を読む全モジュールで同じベクトルになるため、
ランタイムはモジュールごとではなく層ごとに一度回転すればよい。
隠れ次元 5120 がサイズ的に許す 1024 ではなく 128 ブロックで回転されている理由も
おそらくこれ。

**`pre`/`post` の ±2.5% 振幅変調はスケール再フィットではない。** 最小二乗最適値は
平均 0.9215 / 標準偏差 0.0552 なのに、ファイルの `|pre|` は平均 1.0024 /
標準偏差 0.0069 で、振幅同士は無相関 (r = 0.04)。参照実装はこの再フィットを
使っていない。変調の正体は未解明 — 元の列ノルムでも回転後の列ノルムでもなく
(r = 0.007)、同じ活性を見るモジュール間でも層間でも共有されていない。

## 測り方について一つ

参照実装の `blk.0.ffn_gate` 再構成誤差は 0.3673、こちらは同じ形・ビット数・変換で 0.2617。
だがこれを「品質で勝った」と読んではいけない。参照の `s16` はブロック番号とともに
45% 単調増加し、データの rms は平坦なので、ブロックごとの相対誤差は
0.278 から 0.580 へ単調劣化している。これは**重要度（ヘシアン）重み付き割り当てが
そう見える形**でもあり、Frobenius 誤差では両者を区別できない。
だから**ビットストリーム互換性を論文同等の品質として報告してはならない。**
fork 自身の `nariq/cuda-qualification.md` も自分の KL 数値について同じ注意を書いている。

## 再現

```sh
# ベースライン
python convert_hf_to_gguf.py /path/Qwen3.8-27B --outfile bf16.gguf --outtype bf16 --no-mtp
python -m nariq.tools.measure ppl bf16.gguf --ngl 40 --chunks 32

# 一律3ビット + 2ビット埋め込み
CUDA_VISIBLE_DEVICES=4 python -m nariq.export /path/Qwen3.8-27B q27b-3bit \
    --bits 3 --embed-bits 2 --fill 0.95 --verify sample
python -m nariq.tools.evaluate q27b-3bit q27b-3bit.gguf --reference bf16.gguf --skip-dense

# ヘッドだけ差し替える ablation
python -m nariq.tools.graft q27b-3bit q27b-3bit-cal q27b-graft-head --take lm_head
```

一律 3 ビットの全モデル実行は 1 A100 で約 50 分（再フィットと符号化ヘッド込みで 71 分）。
